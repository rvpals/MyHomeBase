MyHomeBase: project insights & reusable blueprint

Written for: someone scaffolding a new Claude-Code-assisted project who wants to copy what works here and skip what doesn't. Every claim cites a path in the repo; guesses are marked GUESS.

1. Overview

A single-developer household web app, built almost entirely with Claude Code. Its leverage comes from one enforced architectural rule plus a small set of docs that tell the agent what to read before acting.

222commits, 2026-07-12 to 2026-11-11
1,813TS/TSX files in src/
~412klines in src/
350test files (all colocated in src/lib)
98domain folders in src/lib/
169numbered SQL migrations
77files in src/cli/

What it is. MyHomeBase bundles a dozen feature modules (investments, journal, expense tracker, classroom, music, games, photos, household, clips, documents, tools) with per-user module access, deployed to a Synology NAS.

Stack (package.json): Next.js 16 App Router, React 19.2.4, TypeScript (strict), Tailwind 4, SQLite via better-sqlite3 12.9, zod 4, Vitest 5, Playwright 1.62, ESLint 9, tsx for scripts. No ORM.

Architecture. All logic lives in src/lib/<domain>/ as plain TypeScript with no React or Next imports. The web app (src/app/) and a CLI (src/cli/) are peer front-ends that only present. Repositories implement interfaces (ports.ts); one composition root (src/lib/wiring.ts) builds real dependencies; tests use hand-written fakes.

2. What makes this project good (ranked by impact)

The top three (an enforced layering rule, a pre-read doc index, and registries that make every "where does X go" question answerable) account for most of the benefit.

1. One hard, machine-enforced architectural rule generic

Practice: nothing in src/lib/ may import react or next, and it is checked twice.

Evidence: eslint.config.mjs (no-restricted-imports scoped to src/lib/**) and scripts/check-lib-boundary.mjs (regex over static, dynamic and require imports; its header explains why a grep one-liner failed on Windows).

Why it helps: the agent gets a binary pass/fail on the most important design decision. Logic cannot drift into components without a red build.

2. A short CLAUDE.md that routes to deeper docs by task generic

Practice: ~1,500 words of "before you do X, read Y" rules instead of a monolith.

Evidence: CLAUDE.md lists triggers: scaffold → ARCHITECTURE.md; UI → components.md; styling → design.md; schema → coding-guide.md; new module → modules.md.

Why it helps: context stays small and relevant. The agent loads a 58k-word registry only when it is about to build UI.

3. Plan-then-wait approval gate generic

Practice: multi-file work needs a written plan (files, migration, icon slots, paid services, open questions) and explicit approval.

Evidence: CLAUDE.md "Plan before building — wait for approval", with a stated exemption list (typos, renames, single-file fixes).

Why it helps: catches misreadings before 400 lines are written, and forces cost questions ("is it free?") up front.

4. Parity between UI and CLI generic idea

Practice: every use-case must run from a terminal too.

Evidence: src/cli/todo.ts imports from @/lib/todo and @/lib/wiring only; CLI_registry.md lists commands and the uncovered use-cases.

Why it helps: the CLI is a litmus test for leaked logic, and gives the agent a way to exercise features without a browser.

5. Registries that make placement mechanical pattern content domain

Practice: modules, components, tables, CLI commands and icon slots each have a registry doc and a naming rule.

Evidence: modules.md (slug / prefix table, retired prefixes), coding-guide.md (three-letter table prefix per module: jrn_, exp_, doc_), components.md.

Why it helps: naming and placement decisions become lookups. Retired prefixes are recorded so they are never reused.

6. Numbered migrations with a human-readable twin generic

Practice: every schema change is NNNN_name.sql plus NNNN_name.md explaining columns, seed data and rollback.

Evidence: migrations/0001_create_modules.{sql,md} through 0169; scripts/migrate.ts backs up the DB first and tracks applied files in sys_schema_migrations.

Why it helps: history is append-only and explained; the agent never edits applied schema.

7. Authorise-first server actions, with the reason written down generic

Practice: every exported action starts with requireModuleAccess(SLUG), requireAdmin() or requireUser().

Evidence: src/app/(protected)/require-access.ts explains that an action is its own POST endpoint, and why slug matching is exact. 84 action files reference a guard (grep count; I did not verify that every exported action is guarded).

Why it helps: a security rule phrased as "first line of every action" is something an agent can follow and a reviewer can scan.

8. Fakes for use-cases, real SQLite for shapes generic

Practice: hand-written in-memory repositories test business rules; real SQLite tests repository contracts.

Evidence: src/lib/household/household.test.ts (FakeHouseholdRepository implements HouseholdRepository) beside repository.test.ts; lessons_learned.md explains why the fake alone missed a data-loss bug.

Why it helps: fast unit tests without hiding the class of bug fakes cannot see.

9. A lessons-learned log of traps, not a changelog generic

Practice: only mistakes whose mechanism generalises, each ending in numbered rules.

Evidence: lessons_learned.md (Partial<> plus ?? "" turning a compile error into silent data loss; debugging the wrong layer). Standing traps are repeated in CLAUDE.md (stale .next, "prove where it renders", uncommitted work is unverified).

Why it helps: converts expensive sessions into rules the next session reads on day one.

10. Safety rails around the production database idea NAS paths

Practice: gates run on a copy and refuse to start if the DB env var is unset or inside the repo.

Evidence: .claude/commands/verify.md ground rules; scripts/prepare-smoke-db.ts, scripts/migration-dry-run.ts; CLAUDE.md "Nothing may touch the real database".

Why it helps: removes the most damaging agent mistake from the list of possibilities.

11. Skills and slash commands for repeatable rituals generic

Evidence: .claude/commands/{verify,release,testing}.md, .claude/skills/build_project/SKILL.md (log change → verify → sync docs → commit, "only when explicitly asked").

Why it helps: multi-step procedures become one invocation with a fixed order.

12. Honest-reporting contract generic

Practice: close each change by listing files touched, what was not verified, and anything unsure.

Evidence: CLAUDE.md "Report done honestly"; it forbids saying "works" on the strength of having written it.

Why it helps: keeps the human's trust calibrated. Note the tension in section 8.

3. Feedback loops

The gates are thorough and ordered cheapest-first, but they are manual: there is no CI and no pre-commit hook, and CLAUDE.md forbids Claude from running them unasked.

StageCommandWhat it checks
Typechecknpm run typechecktsc --noEmit, strict, whole repo including scripts/ and e2e/
Lintnpm run lintESLint 9 with next core-web-vitals + typescript, plus lib import restriction
Boundarynpm run check:lib-boundaryRegex scan of src/lib for react/next imports
Unitnpm testVitest, src/**/*.test.ts only; e2e and .verify/ excluded
Migrationsnpm run db:migrate:dry-runApplies pending migrations to a copy of the dev DB
Preflight / DB prepverify:preflight, verify:prepare-dbEnv safety check, smoke DB in .verify/
Browsernpm run test:e2ePlaywright route sweep: no 4xx/5xx, no React console error, no dev overlay (e2e/smoke.spec.ts)
Allnpm run verifyClears .next first, then chains everything above

Notable design choices. The smoke test discovers module routes from the nav at runtime so new modules are covered automatically. verify clears .next first because stale dev route types break tsc. Tests are colocated and fast because they hit fakes, not the network or a browser. Test files exist only for src/lib (vitest.config.ts includes .test.ts, not .tsx).

Missing: .github/ and .husky/ do not exist. Nothing runs automatically on commit or push.

Adding a feature, walked through with a real example (Household → Recipes)

  1. Prefix and migration: pick hsh_ from coding-guide.md; add migrations/0118_*.sql and its .md.
  2. Library: in src/lib/household/ add types.ts (RecipeSummary, Recipe), schema.ts (zod), ports.ts (interface), repository.ts (SQLite), household.ts (use-cases), export through index.ts.
  3. Tests: household.test.ts with a fake repo; repository.test.ts against real SQLite.
  4. Wire: register the repository in src/lib/wiring.ts.
  5. Action: household-actions.ts with requireModuleAccess("household") on line one, zod-validate, call lib.
  6. View: household-recipes-view.tsx under src/app/(protected)/modules/[slug]/; reuse registered components.
  7. Registration: declare sections, add to module-sections.ts, add to DEFAULT_MODULES and modules.md.
  8. CLI (optional): add src/cli/recipes.ts; list it in CLI_registry.md.

GUESS: the step order is reconstructed from docs and file layout, not from one commit.

6. Documentation and agent guidance

Docs are written for the agent first: imperative, task-triggered, and explicit about the traps. There is no README and no ADR folder.

  • CLAUDE.md (~1,500 words): the router plus the always-on rules and standing traps.
  • ARCHITECTURE.md (~2,800 words): the contract, including "if a request conflicts, stop and flag it".
  • Registries: modules.md (36k words), components.md (59k), CLI_registry.md (31k). Large, but consulted on demand.
  • Decisions as prose in the guides, not ADRs: coding-guide.md explains why pho_ and tol_ were chosen over alb_ and sql_.
  • Comments explain "why": scripts/check-lib-boundary.mjs, eslint.config.mjs (why dist-nas/** is ignored), vitest.config.ts.
  • Deliberately left out: a conventional README, ADR files, CI docs. START_HERE.md is kept but marked historical.

7. Workflow and process

Trunk-based, one developer, release by ritual rather than by pipeline.

  • Branching: everything on main (git status shows branch main; 222 commits).
  • Commit style: descriptive, feature-led, no Conventional Commits. Prefixes recur informally ("Journal:", "Stocks:", "Add"). Only 3 subjects start with "fix". Commits bundle several features.
  • Changelog: CHANGE_HISTORY.md, newest first, tagged [Added]/[Changed]/[Fixed]; Admin → About counts the tags.
  • Release: /build_project (log, verify, sync docs, commit) and /release (back up prod DB, sync docs, commit, push); npm run publish:nas builds the NAS package.
  • Automation: many .bat/.ps1 wrappers at the root (REBUILD_PUBLISH_NAS.bat, START_DEV.bat, full_test.bat).
  • PR/review: none visible. GUESS: solo project, so no review process was needed.

8. Weak spots and risks (do not copy)

The biggest gap is that excellent gates are never automatic.

No CI, no hooks. .github/ and .husky/ are absent. Every gate depends on a human remembering to run it.
"Never run gates unless asked." CLAUDE.md bans verification by Claude because the suite is slow and the DB is on a NAS. The cause (slow suite, risky DB) is the real problem; the rule treats a symptom and moves all verification to the human.
Doc volume. ~300k words of markdown at the root. CHANGE_HISTORY.md alone is ~82k words and components.md ~59k. Registries this size drift; docs even disagree with code (CLI_registry.md says 64 commands, src/cli holds 77 files, GUESS: some are helpers, not commands).
Dead code kept as "cheap revert". ModuleRail and TreeNav have no call sites; CLAUDE.md has to warn the agent about them. Delete dead code and let git be the revert.
Binary and deploy artifacts in the repo. Git history shows NAS_DIST.zip committed then removed (a1794d6, 4416795); dist-nas/ and many root .bat files add noise. Windows-only automation limits portability.
Untested presentation layer. Vitest only collects src/**/*.test.ts; no component tests. The Playwright sweep catches crashes, not wrong behaviour.
Large singletons. src/lib/wiring.ts is 513 lines and grows with every domain; scripts/migrate.ts carries a legacy-rename table that exists only for history.
Personal data guards rely on .gitignore comments. Real statements and rosters are kept out by ignore rules only.

# Project conventions

Strict layering: **all logic lives in `src/lib/`; `src/app/` and `src/cli/` only present.**

## Read the right doc before writing code
- Before scaffolding or changing logic: read `docs/ARCHITECTURE.md`.
- Before schema changes: read `docs/coding-guide.md`.
- Before building UI: read `docs/components.md`; reuse what fits.
- Before adding a {{MODULE_OR_FEATURE_UNIT}}: read `docs/modules.md`.

## Plan before building
For any new feature or multi-file change, present: files to create/modify,
migration, third-party services ({{free or paid?}}), open questions. Then wait for approval.
Exempt: typos, renames, single-file fixes.

## Always-on rules
- `src/lib/` never imports `react` or `next`. Enforced by lint + `npm run check:lib-boundary`.
- Every server action authorises on its first line: {{GUARD_FUNCTIONS}}.
- Validate boundary input with the domain's zod schema.
- New lib logic ships with a colocated `*.test.ts` (success + failure paths).
- Every use-case must be callable from {{WEB}} and {{CLI_OR_JOB}}.
- Never touch {{PRODUCTION_DATA_STORE}}; scripts must use {{ENV_VAR}} and refuse unsafe paths.

## Verification
- Run `npm run verify` before reporting done ({{typecheck, lint, boundary, unit, e2e}}).
- CI runs the same command on every push.
- Report: files changed, what was NOT verified, anything unsure.

Top 5 insights

  1. Enforce one architectural rule mechanically. The src/lib framework-free boundary is checked by lint and a script, so layering survives hundreds of AI-written changes.
  2. Keep CLAUDE.md a router, not an encyclopedia. Task-triggered "read X before Y" lines keep context small while deep docs stay available.
  3. Make placement a lookup. Registries and naming rules (table prefixes, module slugs, component list) remove judgment calls an agent would get wrong.
  4. Write down failures as rules. lessons_learned.md and the standing traps turn costly sessions into durable guidance.
  5. Automate the gates; don't copy the manual-only approach. Verification is thorough but depends on a human; a new project should put the same chain in CI and a hook.
