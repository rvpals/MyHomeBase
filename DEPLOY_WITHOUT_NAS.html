Deploy Without NAS

Build on a dev machine, copy from any machine that can reach the NAS.

When to use this

The normal deploy is one command — REBUILD_PUBLISH_NAS.bat — but it needs the repo, Node.js, npm, and the NAS all on the same machine. Use the two-step split when the build machine can't reach the NAS, or the machine with NAS access doesn't have the dev toolchain:

  • The dev machine has the repo and Node but no NAS access
  • A second machine (or the same one, later) has NAS access but no repo or npm
  • You want to inspect the build before shipping it

The two scripts

ScriptWhat it doesNAS needed?
REBUILD_FOR_NAS.bat Builds the aarch64 package into dist-nas\ No
COPY_TO_NAS.bat Copies the build to the NAS, triggers a restart Yes

Together they do exactly what REBUILD_PUBLISH_NAS.bat does — same build command, same robocopy, same deploy trigger, same exclusions.

Step by step

On the dev machine (has the repo, Node, npm — no NAS access needed)

1
Build the aarch64 package 
cd C:\git\MyHomeBase
.\REBUILD_FOR_NAS.bat

This runs npm run publish:nas, which does a production build, swaps in the arm64 better-sqlite3 prebuild, and bundles the migration runner (migrate.cjs). Output lands in dist-nas\ by default.

To use a different output folder:

.\REBUILD_FOR_NAS.bat D:\staging\nas-build
2
Transfer the build + copy script

Copy two things to the machine that can reach the NAS (USB drive, file share, cloud storage — whatever works):

WhatWhy
The entire dist-nas\ folder The self-contained app — everything the NAS needs to run
COPY_TO_NAS.bat The copy script — standalone, no repo or Node required

Put them in the same folder on the destination machine. The script looks for dist-nas\ next to itself by default, or pass a path argument to point it elsewhere.

On the machine with NAS access (no repo, Node, or npm needed)

3
Copy to the NAS 
.\COPY_TO_NAS.bat

This does four things in order:

  1. Checks that \\NAS_DS223\app\myhomebase is reachable
  2. Writes deploy.trigger before the copy (so the restart overlaps with the file transfer — a few seconds of "connection refused" instead of up to a minute of 500s from a half-replaced build)
  3. Robocopy /MIR mirrors the build to the NAS
  4. Prints post-deploy guidance (.env, start.sh, migration reminders)

If the build folder is somewhere else:

.\COPY_TO_NAS.bat D:\transfers\dist-nas

The copy machine only needs Windows and network access to the NAS share. No Node, no npm, no repo — COPY_TO_NAS.bat is a plain batch file that calls robocopy.

4
Wait for the restart — automatic, under a minute

The NAS keepalive task runs every minute. When it sees deploy.trigger, it stops the old process, runs migrations, and starts the new build. To force it immediately:

DSM → Task Scheduler → select "MyHomeBase keepalive" → Run

What gets preserved on the NAS

Robocopy /MIR deletes files that are no longer in the build — but these are always excluded and never touched:

ExcludedWhy
data\The production database
.envSecrets (DB path, Google OAuth, signup secret)
start.shNAS-side launcher — created once, never shipped
app.logRuntime log
app.pidRunning process PID
fallback.pidFallback process PID
deploy.triggerJust written — excluded so /MIR doesn't delete it

Migrations

Migrations are automatic. The build includes migrate.cjs (bundled by publish-nas.mjs). When start.sh detects a triggered deploy, it runs migrate.cjs before starting the app. The migration runner:

  • Takes a timestamped backup of the database first
  • Applies any pending .sql files from migrations/
  • Aborts startup on failure — the keepalive retries every minute and app.log shows what broke
Note: To run migrations manually (diagnosing a failure, or applying before the automatic restart): 
cd /volume1/app/myhomebase && node --env-file-if-exists=.env migrate.cjs

Configurable defaults

Both scripts have variables at the top you can edit:

ScriptVariableDefault
REBUILD_FOR_NAS.bat OUTPUT_DIR dist-nas (relative to repo root)
COPY_TO_NAS.bat SOURCE_DIR dist-nas (relative to repo root)
NAS_PATH \\NAS_DS223\app\myhomebase

A command-line argument overrides the folder in both scripts. Edit NAS_PATH inside COPY_TO_NAS.bat if the NAS share path changes.

Troubleshooting

"Cannot reach" the NAS path

  • Is the NAS powered on and on the network?
  • Can you open \\NAS_DS223 in Explorer?
  • Windows may need credentials — open the share in Explorer once and tick "Remember my credentials"

App shows 500s or won't load after deploy

Wait up to 2 minutes. If still down, open the app in a browser — start.sh serves the last 100 lines of app.log as a diagnostic page when server.js can't start. The keepalive task retries every minute.

ABI mismatch after a DSM Node upgrade

If app.log shows NODE_MODULE_VERSION errors, the better-sqlite3 native binary doesn't match the NAS's Node version. Check the ABI on the NAS:

node -p process.versions.modules    # over SSH

Then rebuild with the correct ABI:

set NAS_NODE_ABI=127
.\REBUILD_FOR_NAS.bat

Failure page never appears

The NAS-side start.sh is not shipped by the publish. If it's missing or outdated, run:

.\COPY_NAS_START_SH.bat myuser
Never point any script or migration at the production database directly. The live DB is on the NAS at /volume1/app/myhomebase/data/. The repo's data/ folder is a stale local copy.
